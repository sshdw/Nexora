# Nexora CLI — Product, Architecture & Design Brief

**Статус:** финальный целевой бриф для проектирования Nexora CLI  
**Продукт:** Nexora CLI — локально-ориентированный AI coding agent с интерактивным TUI и обычным CLI-режимом  
**Связанный продукт:** Nexora Desktop 2.x  
**Основная платформа:** Windows 11, Windows Terminal, PowerShell 7/Windows PowerShell 5.1, терминал VS Code и Windows Console/ConPTY  
**Рекомендуемый стек:** Rust + Ratatui + Crossterm + Clap; существующие Rust-сервисы Nexora, SQLite и системное хранилище секретов — общие для Desktop и CLI  
**Важно:** это целевое описание продукта и требований, а не план разработки. Команды и интерфейсы ниже — спецификация будущего поведения, а не заявление, что они уже реализованы.

---

# 0. Главное решение

> **Nexora CLI должен быть спокойным, компактным, agent-first рабочим пространством внутри терминала: он показывает, что агент делает и что изменилось, сохраняет контекст и даёт человеку контроль — не превращая консоль в перегруженный псевдографический dashboard.**

CLI — не набор несвязанных команд и не копия Desktop с нарисованными рамками. Это второй интерфейс Nexora с собственным способом взаимодействия:

- в интерактивном режиме — полноценный TUI, которым удобно управлять часами;
- в обычном CLI-режиме — предсказуемые команды для скриптов, пайплайнов и автоматизации;
- логика провайдеров, агентного цикла, разрешений, хранения и обработки ошибок должна быть общей с Desktop там, где это технически возможно;
- интерфейс терминала не должен зависеть от React, браузерного рендеринга или Tauri.

Короткое описание характера: **Quiet Terminal Workspace** — `quiet · technical · dense · predictable · agent-native`.

# 1. Что именно представляет собой CLI

## 1.1 Два способа использования

### Интерактивный TUI

Основной пользовательский режим. Пользователь открывает Nexora, пишет задачу, наблюдает за работой агента, инспектирует tool calls и diff, принимает решения по approvals, просматривает прошлые сессии и продолжает работу.

Ожидаемое поведение:

- `nexora` без аргументов запускает TUI, если stdin/stdout — интерактивный терминал;
- интерфейс сохраняет историю и черновик при переходах между временными экранами;
- основной сценарий доступен клавиатурой; мышь — дополнительное удобство;
- выполнение агента не блокирует перерисовку интерфейса;
- выход всегда корректно возвращает терминал в исходное состояние.

### Обычный CLI

Предназначен для быстрого запуска, автоматизации, интеграции со скриптами и вызова из других инструментов.

Примеры целевого интерфейса:

```powershell
nexora --help
nexora --version
nexora run "Fix the authentication flow and run tests"
nexora run "Explain this error" --format json
nexora sessions list
nexora models list
nexora providers list
nexora doctor
```

Команды должны быть стабильными и документированными. При перенаправлении вывода, работе из CI или при отсутствии TTY Nexora не должен самопроизвольно запускать полноэкранный TUI.

## 1.2 Для кого это

- разработчик, который хочет поручить задачу агенту, не выходя из терминала;
- пользователь Windows, работающий в PowerShell или VS Code Terminal;
- пользователь, который хочет видеть реальные шаги агента, а не только финальный ответ;
- разработчик, автоматизирующий повторяемые действия скриптами;
- пользователь Nexora Desktop, которому нужна одна история, один список провайдеров и общие настройки.

## 1.3 Не цель продукта

Не нужно делать из CLI:

- копию Desktop, где каждая панель нарисована рамками;
- оболочку, которая требует мышь, Nerd Font или конкретную цветовую схему;
- мониторинг-дашборд из десятков постоянных показателей;
- отдельного агента, который отличается от Desktop поведением и правилами безопасности;
- конкурирующую реализацию провайдеров и SQLite-схемы;
- обязательный облачный аккаунт или удалённую синхронизацию;
- графический терминал со стеклом, тенями, псевдо-прозрачностью и непрерывными эффектами.

# 2. Технические решения и языки

## 2.1 Рекомендуемый стек

| Слой | Технология | Назначение |
|---|---|---|
| Язык CLI и TUI | **Rust** | Безопасная нативная программа, доступ к существующим backend-модулям Nexora |
| Полноэкранный интерфейс | **Ratatui** | Разметка терминального экрана, списки, текст, diff, панели и scroll regions |
| Терминал, события клавиатуры/мыши | **Crossterm** | Ввод, raw mode, alternate screen, перемещение курсора, resize events, цвета |
| Аргументы и подкоманды | **Clap** с derive API | `run`, `sessions`, `models`, `providers`, `config`, `doctor`, `--help` |
| Модели обмена данными | **Serde + serde_json** | Структуры запросов/ответов, JSON output, сериализация событий |
| Хранилище | **Существующий SQLite слой Nexora** | История, настройки, runs, steps и другие уже определённые данные |
| Секреты | **Существующий `keyring` слой** | API-ключи через системное хранилище, не открытый текстовый файл |
| HTTP | **Существующий клиент provider layer** | Не создавать отдельные реализации API только для CLI |
| Ошибки и диагностика | Существующая классификация ошибок, общий logging facade | Единые сообщения и диагностика Desktop/CLI |
| Тесты UI | Ratatui `TestBackend` + unit/integration tests | Проверка отрисовки и состояний без реального терминала |

На дату подготовки этого документа официальная документация Ratatui показывает версию 0.30.2 и требует Rust 1.88 или новее; типичная связка — Ratatui с Crossterm 0.29. Конкретные версии нужно согласовать с toolchain репозитория, а не механически обновлять всё до latest. Ссылки на официальные документы находятся в конце файла.

## 2.2 Почему именно Rust

Существующий Nexora уже построен на Tauri v2 + React 19 + TypeScript во frontend и Rust в backend. Провайдеры, agent runner, управление разрешениями, бюджетами и частью персистентности находятся в Rust. Для CLI Rust позволяет повторно использовать этот слой без запуска браузерного UI.

**TypeScript не нужен для основного CLI.** Он остаётся языком Desktop. Не нужно делать второй CLI на Node.js только потому, что Desktop использует React/TypeScript: это дублирует интеграцию с агентом, настройками, БД и секретами.

## 2.3 Библиотеки не являются архитектурой

Ratatui/Crossterm/Clap отвечают за оболочку. Они не должны содержать бизнес-логику Nexora.

Обязательное разделение:

- **shared core:** сценарии приложения, модели данных, агентный запуск, правила approvals, провайдеры и единая классификация ошибок;
- **desktop adapter:** Tauri IPC-команды и интеграция с оконным приложением;
- **CLI adapter:** аргументы, TUI, ввод/вывод, форматированный вывод, exit codes;
- **storage/infrastructure:** общие SQLite-репозитории, keyring, HTTP-клиенты, системные операции.

## 2.4 Важная особенность текущей структуры Nexora

Сейчас backend находится в crate `src-tauri`, который зависит от `tauri` и содержит внутренние модули. CLI не должен пытаться ссылаться на него как на готовую независимую библиотеку без изменений: Tauri-specific команды и зависимости затрудняют такое переиспользование.

Целевая архитектура должна отделять общий код так, чтобы:

- shared crates **не зависели** от Tauri, React, Ratatui или Clap;
- Tauri-команды были тонкими адаптерами над общими application services;
- CLI обращался к тем же application services напрямую;
- desktop и CLI не имели разных реализаций одного и того же правила;
- UI-обновление не требовало менять runner, а изменение agent core не требовало переписывать TUI.

Не нужно заранее создавать десятки мелких crates. Разделение должно следовать настоящим границам существующей архитектуры и вводиться настолько крупными частями, насколько это удобно сопровождать.

Пример целевого направления, а не обязательного буквального дерева:

```text
Nexora workspace
├─ crates/
│  ├─ nexora-core/            # domain + application services/use cases
│  ├─ nexora-providers/       # provider clients, normalized responses
│  ├─ nexora-storage/         # SQLite repositories + migrations
│  └─ nexora-workspace/       # filesystem/tools/permission boundaries
├─ apps/
│  └─ nexora-cli/             # Clap + Ratatui + Crossterm
└─ src-tauri/                 # Tauri shell + React desktop bridge
```

Это схема назначения модулей, не требование сохранить именно такие имена и число crates. Решение по фактическому разбиению должно учитывать текущие зависимости исходников.

## 2.5 Асинхронная работа и отзывчивость

Пока агент ждёт сеть, читает файлы или запускает команду, TUI обязан оставаться отзывчивым. Перерисовка экрана не должна ожидать завершения HTTP-запроса или процесса.

Правило реализации:

- долгие операции выполняются в worker thread/process или в существующем поддерживаемом execution mechanism;
- события идут в TUI через channel/event queue;
- основной цикл TUI отвечает за ввод, обновление состояния и rendering;
- отмена, pause/resume, approvals и progress events должны доставляться без блокировки интерфейса;
- **не вводить Tokio только по привычке**: текущая provider-часть использует blocking `reqwest`, поэтому надо сперва использовать существующий подход с worker threads/channels либо обосновать async-runtime реальной необходимостью;
- любой запуск процесса должен иметь управляемую отмену, таймауты и корректную обработку завершения.

# 3. Связь с Nexora Desktop

## 3.1 Одна система, два интерфейса

CLI и Desktop должны быть разными способами работать с одной системой, а не двумя независимыми приложениями.

Общими должны быть, где применимо:

- список AI-провайдеров и поддерживаемых моделей;
- логика выбора провайдера/модели;
- агентный цикл и tool registry;
- режимы автономности и риск-политика;
- pause/resume/cancel и лимит итераций;
- лимит расходов и подсчёт затрат;
- SQLite-схема, migrations и репозитории;
- история разговоров и runs;
- системное хранилище API-ключей;
- обработка ошибок и правила retry;
- доступ к workspace и файловым операциям;
- поведение, когда провайдер недоступен или credential отсутствует.

## 3.2 Единые данные

Если пользователь создаёт или продолжает поддерживаемую сессию из Desktop или CLI, Nexora должен работать с общим источником данных. Не создавать отдельную `nexora-cli.db`, если нет технически необходимой и явно обоснованной причины.

Нужно использовать тот же официальный app-data namespace/path resolver, что и Desktop. Не угадывать путь по имени папки и не заводить отдельное хранилище только ради упрощения CLI.

Для общих SQLite-файлов обязательны:

- migrations от общего слоя;
- безопасная работа, если Desktop и CLI одновременно открыты;
- транзакции и согласованность run/step history;
- корректное поведение при блокировке БД или ошибке migration;
- отсутствие миграций, применяемых только в одном приложении и несовместимых со вторым.

## 3.3 Общие секреты

API-ключи должны оставаться в том же системном keyring namespace, которым управляет Desktop. Запрещено:

- сохранять ключи в SQLite;
- показывать ключи в терминале целиком;
- записывать ключи и заголовки авторизации в логи;
- добавлять ключи в command history или arguments по умолчанию;
- выводить секреты в `doctor`, debug dumps или JSON events.

Если ключ не настроен, CLI даёт безопасный путь настройки через интерактивный prompt либо поддерживаемую команду настройки. Ввод секрета должен быть скрытым, где это поддерживается.

## 3.4 Desktop-only возможности

Функции, которые требуют окна или специфичной графики, могут не иметь прямого аналога в CLI. Их следует адаптировать под текстовый интерфейс, а не строить фиктивные реализации. Настройки внешнего вида терминала не должны менять тему Desktop без явного общего пользовательского выбора.

# 4. Принципы дизайна CLI

## 4.1 Визуальный характер

**Quiet Terminal Workspace** — не cyberpunk, не ретро-hacker green, не неоновый AI и не псевдографическая копия desktop-окна.

Визуальный язык:

- тёмный и спокойный, но цветовая схема по умолчанию уважает цвет фона и текста терминала пользователя;
- плотный: больше полезной информации на экран, меньше декоративных строк;
- технический: выровненные данные, ясные названия файлов и tool calls;
- нейтральный: одно приглушённое основное выделение, минимум вспомогательных цветов;
- функциональный: символы и цвет подкрепляют текст, но не заменяют его;
- стабильный: панели и основные действия не прыгают с места на место;
- живой только в моменты реальной работы, а не в idle.

## 4.2 Жёсткие запреты

Не использовать:

- градиенты, glow, псевдо-прозрачность и glassmorphism;
- ANSI rainbow или отдельный цвет каждому элементу;
- огромные ASCII-логотипы на каждом запуске;
- постоянные большие рамки вокруг каждого tool call;
- прогресс-бары, которые ничего не измеряют;
- бесконечные пульсации и мерцание;
- обилие emoji и символов, которые по-разному отображаются шрифтами;
- зависимость от Nerd Fonts;
- частую перерисовку всего экрана без реального изменения;
- сообщения `Thinking...` без дополнительного смысла, когда есть реальное состояние;
- постоянные status counters, которые не помогают текущей задаче;
- автоматический scroll к низу вопреки действию пользователя;
- обязательные mouse-hover элементы для основных действий;
- внезапные новые постоянные панели.

## 4.3 Палитра и семантические цвета

CLI не должен жёстко навязывать пользователю цвет фона. Предпочтительно применять foreground styles к конкретному тексту и использовать фон терминала по умолчанию.

Целевые смысловые роли:

| Роль | Вид | Значение |
|---|---|---|
| Primary / active | приглушённый amber, если цвет доступен | текущий фокус, активная строка, важное действие |
| Normal | цвет терминала по умолчанию | основной текст и результат модели |
| Muted | dim/gray | время, вторичная метаинформация, старые события |
| Success | приглушённый sage/green | действие завершилось, тесты прошли |
| Warning | приглушённый ochre/yellow | внимание, ограничение, ожидающее решение |
| Error | спокойный brick/red | ошибка, отказ, рискованное действие |
| Border / guide | серый/низкий контраст | разделение смысловых зон |

Цвета не должны означать две вещи одновременно. Статус дополнительно обозначается текстом или символом: `✓ Done`, `! Failed`, `? Approval required`. В режиме без цвета вся информация сохраняется.

Нужно поддержать уровни возможностей:

- auto — определить возможности среды настолько надёжно, насколько возможно;
- basic/16-color;
- 256-color;
- truecolor, если терминал и конфигурация его поддерживают;
- no-color, принудительно.

Учитывать `NO_COLOR`, redirected stdout/stderr, наличие интерактивного TTY и явные флаги пользователя. Не полагаться на один env var как на абсолютное доказательство возможностей терминала.

## 4.4 Unicode и ASCII

Предпочтительный вид использует простые line-drawing символы, например `│`, `─`, `└`, если они поддерживаются нормально. Должен существовать ASCII fallback:

```text
Unicode:  │  └─  ✓  →
ASCII:    |  +-- [ok] ->
```

Нельзя требовать определённый шрифт. Не использовать emoji как обязательные индикаторы. Сложные wide glyphs могут ломать выравнивание — тестировать на распространённых Windows Terminal/PowerShell шрифтах и в ASCII-режиме.

## 4.5 Типографика

CLI не контролирует семейство, размер и вес шрифта. Иерархия строится через:

- отступы;
- короткие заголовки;
- редкие uppercase labels;
- выравнивание колонок;
- тонкие разделители;
- нормальный/приглушённый текст;
- ограниченное жирное начертание.

Не имитировать веб-шрифтовую иерархию десятками стилей. Основной контент должен читаться без цветового различия.

# 5. Основной экран TUI — полное описание

## 5.1 Основная структура

На типичном терминале шириной примерно 100–130 колонок и высотой 28–40 строк основное пространство состоит из четырёх зон:

1. **Status line** — один тонкий ряд наверху: Nexora, проект/workspace, git branch/state если известно, текущий provider/model и статус run.
2. **Conversation / Run timeline** — основное пространство экрана: пользовательские запросы, ответы агента, tool events, diff summary, errors и approvals.
3. **Composer** — поле ввода внизу; сохраняет черновик, использует доступную ширину и расширяется по содержимому в заданных пределах.
4. **Key hints** — одна компактная строка подсказок для наиболее полезных действий в текущем состоянии.

Не делать видимую слева панель истории обязательной по умолчанию. История сессий открывается отдельной командой/overlay; это оставляет максимум места центральной задаче. Если понадобится navigation list, он появляется по запросу или в достаточно широком терминале.

## 5.2 Пример обычного активного экрана

```text
 NEXORA  ~/projects/nx  main*                   Opus · semi-auto · RUNNING
────────────────────────────────────────────────────────────────────────────

 Fix authentication

 You
 Fix the auth flow and run the tests.

 Nexora
 │  Read      src/auth.ts
 │  Read      src/session.ts
 │  Search    "refreshToken" · 7 matches
 │  Edit      src/auth.ts                         +24  -8
 │  Test      npm test
 │
 └─ ✓ 42 tests passed

 Working · 4 files touched · 18s

────────────────────────────────────────────────────────────────────────────
 › Ask Nexora anything...
   Enter send · Ctrl+J newline · Ctrl+K commands · Esc close
```

Правила примера:

- основная лента не оборачивает каждое событие в рамку;
- tool-call — строка состояния с кратким названием, путём и итогом;
- детали раскрываются по запросу;
- user prompt и ответ агента различимы по подписи и отступам, не по огромным bubble backgrounds;
- composer отделён одним тонким разделителем;
- метаданные видны, но не конкурируют с содержимым.

## 5.3 Статусная строка

Она должна отвечать на вопросы: «Где я?», «Какой режим/модель?», «Агент работает или ждёт?». Не надо включать все доступные сведения одновременно.

Состав:

- короткое имя проекта или выбранная папка;
- git branch, если это рабочая папка Git и branch доступна;
- provider/model, при нехватке места — сокращённое, раскрываемое через status/info command;
- короткий статус: `IDLE`, `RUNNING`, `PAUSED`, `WAITING APPROVAL`, `FAILED`;
- при необходимости — индикатор незакоммиченных изменений, без обещания полного статуса Git, если проверка не выполнена.

Не помещать в строку по умолчанию token counts, цену, полный путь, количество всех файлов, версию приложения, иконки каждой подсистемы. Эти сведения — в detail/status overlay.

## 5.4 Composer

Composer — одна из главных точек управления. Он должен ощущаться как устойчивое место ввода, а не всплывающая карточка.

Требования:

- один визуально ясный префикс `›` или `>`;
- длинный текст переносится на новые строки и остаётся редактируемым;
- в обычном интерактивном режиме отправка не происходит случайно от вставки многострочного текста;
- поддерживаются вставка текста и пути файла;
- пустой composer показывает ненавязчивую инструкцию, а не огромный placeholder;
- draft переживает открытие settings/help/sessions/terminal/diff views и переключение сессии;
- отправленная задача добавляется в историю ровно один раз;
- ошибка отправки не уничтожает draft — текст можно исправить и повторить;
- текущая модель/режим показаны кратко в footer или через contextual hint;
- attachments, если поддерживаются, должны быть явно перечислены и удаляемы до отправки.

Целевые клавиши ввода:

- `Enter` — отправить, если композиция в отправляемом состоянии;
- `Ctrl+J` — новая строка, работает как надёжный fallback;
- `Shift+Enter` — новая строка только если текущий терминал передаёт эту комбинацию надёжно;
- `Esc` — сначала закрывает открытый overlay/autocomplete; не удаляет draft молча;
- `Ctrl+K` — command palette;
- `Ctrl+C` при активном run — запросить отмену текущего run, с ясной обратной связью; отдельное действие выхода не должно происходить случайно.

Если некоторые комбинации конфликтуют с терминалом/host shell, их можно переназначить. Приложение должно иметь `nexora keys`/help screen с актуальной картой управления. Основные операции нельзя привязывать исключительно к недоступным на части терминалов сочетаниям.

## 5.5 Масштабируемая разметка

Рекомендуемые поведения:

- **широкий терминал:** центральная лента имеет читаемую максимальную ширину; detail panel может появляться справа только по запросу;
- **средний терминал:** одна основная колонка, без постоянной правой панели;
- **узкий терминал:** скрывать необязательные метаданные, переносить подписи/пути, не обрезать единственным способом доступные действия;
- **низкая высота окна:** компактные key hints, уменьшение числа видимых элементов, composer с ограниченной высотой;
- **resize:** не сбрасывает содержимое, позицию прокрутки, черновик или выбранный объект;
- если размеры действительно слишком малы, показывать ясное `Terminal too small — enlarge window or switch to compact mode`, а не рисовать разрушенный интерфейс.

Точные thresholds должны быть конфигурируемыми на уровне layout и проверяться тестами. Не считать одну ширину универсальной для всех шрифтов.

# 6. Экраны и состояния

## 6.1 Первый запуск / no provider

Никакого огромного ASCII-арта. Пример:

```text
Nexora CLI
Local-first AI agent workspace

No AI provider is configured.

  1  Configure a provider
  2  View supported providers
  3  Exit

↑/↓ navigate · Enter select · Esc back
```

Первый запуск должен:

- объяснить, что требуется для обращения к модели;
- показать поддерживаемые провайдеры из общего source of truth;
- дать безопасно настроить credential;
- не требовать аккаунт Nexora или cloud sync;
- не отправлять запросы в сеть просто при запуске;
- не создавать фиктивную сессию или пустой run.

## 6.2 Пустая сессия

```text
New conversation

Describe a task, ask a question, or reference a file path.

›
```

Уместные короткие примеры можно показать как текст под вводом, но не превращать весь экран в стартовый dashboard.

## 6.3 Запуск агента

Каждый run показывает:

- начальный запрос;
- статусную последовательность, когда она реально сообщается core;
- tool calls в порядке выполнения;
- успешный/неуспешный результат вызова;
- безопасные сведения о файлах и командах;
- approvals, pause/resume/cancel;
- итог агента и агрегированный результат.

Состояния отображать только на основании реальных событий. Не симулировать `Planning`, `Reading` или проценты, если core их не выдаёт. Если доступно только состояние `Working`, показывать `Working`, а не придумывать псевдо-прозрачность процесса.

## 6.4 Пауза

```text
│  Test      npm test
│  … paused

Run paused · 4 steps completed
[R] Resume   [C] Cancel   [Esc] Close details
```

Пауза должна быть настоящим состоянием выполнения, а не просто stop rendering. Если текущий tool/process нельзя безопасно остановить мгновенно, интерфейс обязан сообщить `Pausing after current operation`.

## 6.5 Approval required

```text
! Approval required

The agent wants to run:
  npm test -- --updateSnapshot

Working directory:
  C:\projects\nx

Reason / risk:
  This command may rewrite snapshot files.

[A] Approve once   [D] Deny   [I] Inspect command   [Esc] Decide later
```

Approval не должен превращаться в неожиданную модальную блокировку всего экрана. Это ясный блок в timeline, который сохраняет контекст. Пользователь видит, какое действие ожидает решения, почему оно требует решения и что произойдёт после подтверждения.

Правила:

- parked approvals не одобряются автоматически;
- `Esc`/открытие другой панели не означает approve или deny;
- решение пишется в историю run;
- у решения есть определённые keyboard bindings;
- команда, cwd, затронутый ресурс и класс риска показаны до подтверждения;
- длинная команда переносится аккуратно, её можно раскрыть целиком и скопировать;
- в non-interactive режиме действия, требующие human approval, нельзя беззвучно подтверждать.

## 6.6 Diff view

Diff — отдельный detail view, который не уничтожает историю чата.

Требования:

- группировка по файлам;
- `+`/`-` и цвет — оба различают добавления и удаления;
- длинные строки можно просмотреть целиком или прокрутить по горизонтали;
- виден относительный или полный путь и итоговые `+N -M`;
- можно переходить к следующему/предыдущему изменённому файлу;
- копирование пути и фрагмента — доступно клавиатурой;
- при закрытии возвращается тот же run и позиция в истории;
- файл, который изменил агент, не выдаётся за изменение, подтверждённое Git commit;
- текстовый diff не должен автоматически исполняться или применяться только потому, что пользователь открыл его.

## 6.7 История сессий

```text
Sessions

  Fix authentication             completed   18m ago
  Refactor API client              paused     yesterday
  Explain build failure           completed   yesterday
  UI polish                         failed    Oct 03

Type to filter · Enter open · D delete · Esc back
```

Список должен быть лёгким и ориентированным на поиск:

- быстрый фильтр по названию/тексту, если доступен общий search index;
- статус и время — вторичная информация;
- активная сессия и незавершённый run различимы;
- удаление всегда ясно подтверждается, если оно окончательное;
- archived/restored semantics должны совпадать с Desktop, если эти операции доступны;
- пустой результат объясняет, что фильтр ничего не нашёл;
- открытие старой сессии не запускает автоматически агента.

## 6.8 Command palette

`Ctrl+K` открывает компактный поиск команд:

```text
Command
> switch model

  Switch model
  New conversation
  Open sessions
  View diff
  Pause current run
  Open settings
```

Правила:

- фильтр реагирует сразу;
- recent commands выделяются весом/контрастом, а не ярким accent;
- команды недоступны в текущем состоянии — скрыты или отмечены как disabled с причиной;
- действие не выполняется до явного выбора;
- закрытие сохраняет состояние текущего run и composer;
- названия команд едины с обычным `--help` и документацией.

## 6.9 Settings / provider / model selection

Не строить отдельный мини-dashboard. Использовать текстовые списки, короткие формы и понятные значения.

Provider list показывает:

- имя провайдера;
- настроен credential или нет;
- выбран ли он по умолчанию;
- число/перечень моделей — по раскрытию.

Model picker показывает реальные модели, доступные от общего provider registry. Если пользователь ввёл custom model ID, это должно быть видно как custom ID и обрабатываться так же, как в Desktop, без самовольного переименования.

Изменение model/provider не должно незаметно менять уже запущенный run. Текущий run сохраняет те настройки, с которыми он был запущен, если backend contract не определяет иначе.

## 6.10 Terminal / external command

Если Nexora показывает вывод выполненной команды:

- сохранять stdout и stderr раздельно в модели события, если они раздельны в backend;
- показывать exit code и duration;
- длинные логи сворачивать после того, как пользователь уже видел важный итог, но не уничтожать оригинальные данные;
- по умолчанию не очищать экран внешней команды так, чтобы потерять контекст Nexora;
- команды с destructive effects требуют соответствующей approval policy;
- содержимое вывода не считается доверенными инструкциями системе или модели;
- secrets и environment values должны редактироваться, если они известны как sensitive.

## 6.11 Help и диагностика

`F1` или command palette открывает help с командами, клавишами и текущим контекстом. `nexora doctor` выводит полезную диагностику:

- версия CLI и версия core;
- OS и shell/terminal capability summary;
- доступность app-data directory и SQLite;
- состояние migrations;
- доступность keyring без значений secrets;
- доступные provider definitions и статус credential (настроен/не настроен);
- возможные проблемы запуска процессов/прав доступа;
- способ включить debug logging и расположение логов.

`doctor` не должен делать платные AI-запросы автоматически. Провайдерный network check можно сделать отдельным явным действием.

# 7. Единый язык событий агента

## 7.1 Agent Activity Spine в терминале

Фирменная деталь Nexora — вертикальная линия, связывающая шаги одного run. В TUI это не animated loading bar; это простая временная структура.

```text
│  Read     src/auth.ts
│  Read     src/session.ts
│  Search   "refreshToken" · 7 matches
│  Edit     src/auth.ts                   +24 -8
│  Run      npm test
└─ ✓ 42 tests passed
```

Требования:

- события отображаются в хронологическом порядке;
- иконка/символ не должен быть единственным способом понять тип;
- текущее действие можно раскрыть;
- старые действия могут тускнеть только как вторичная информация — тело результата остаётся читаемым;
- событие не удаляется из истории только из-за fade;
- error и approval сохраняются заметными до осмысленного разрешения;
- при `prefers-reduced-motion` аналогом является отключённая анимация; в CLI пользователь должен иметь настройку motion none/quiet/normal.

## 7.2 Нормализованные типы событий

TUI должен отображать реальную модель событий, а не разбирать текстовые логи по регулярным выражениям.

Минимальные семантические классы:

- run started;
- assistant status/progress, если core его выдаёт;
- model response / final response;
- tool call started;
- tool call completed;
- tool call failed;
- approval required / approved / denied;
- run paused / resumed / cancelled;
- step budget exhausted;
- spend limit exceeded;
- run completed;
- provider/network/auth error;
- changed-file/diff summary, когда он доступен.

Каждое событие должно иметь стабильный идентификатор или последовательность, временную отметку и достаточные поля для render/details. Секреты, opaque provider reasoning signatures и другие чувствительные внутренние данные не выводятся.

## 7.3 Завершённый run

Успешный run не должен выбрасывать праздничную анимацию или огромный зелёный блок. Пример:

```text
✓ Completed · 18s
  4 files touched · 42 tests passed
```

Если статистика неизвестна — не выдумывать её. Если изменённых файлов нет, это не ошибка. Если результат пустой или изменений не было, сообщить понятным текстом.

## 7.4 Ошибка и восстановление

```text
! Command failed · exit 1
  npm test
  2 tests failed

  [R] Retry   [I] Inspect output   [C] Copy details
```

- ошибка остаётся доступной после других действий;
- stack trace и полные логи раскрываются по запросу;
- кнопки/shortcut labels меняются по состоянию;
- после успешного retry старый failure становится историческим событием, но не исчезает из audit/run history;
- нельзя окрашивать весь экран красным;
- нельзя скрывать причину за одним generic `Something went wrong`.

# 8. Micro-UX: обязательное поведение

Фишки из Desktop Design Brief адаптируются под терминал только там, где это имеет смысл. Не переносить все эффекты механически.

## 8.1 Приоритетные micro-interactions

### Scroll Hold

Когда пользователь прокрутил timeline выше нижнего края, новые события не перемещают его viewport. В нижней строке появляется компактная подсказка вида `↓ 8 new events · 12 tok/s`. Enter/click возвращает к актуальному событию. Новые события не теряются.

### Tool Group Folding

Завершённые группы мелких tool calls могут сворачиваться в `12 calls · 4 files · 2 commands`. Ошибки и ожидающие approvals автоматически не прячутся в сводку. Раскрытие показывает оригинальные события в том же порядке.

### Focus Memory

Открытие command palette, sessions, diff, help или provider list не должно сбрасывать текущий run, draft или позицию в timeline. После закрытия возвращается прежний рабочий контекст, если данные ещё существуют.

### Approval Return Point

После принятия решения по approval пользователь видит, что оно принято, и где агент продолжил. Если агент продолжить не смог, показывается причина — нельзя визуально обещать продолжение, пока core его не подтвердил.

### File Touch Trace

Недавно изменённые файлы получают тонкий `│` или аналогичный текстовый маркер в дереве/списке diff. Маркер может со временем стать менее заметным, но файл не должен терять доступность или историю.

### Quiet Copy

После copy текущий элемент временно показывает `Copied`. Никакого toast, если inline feedback достаточен. Для обычного CLI, где нет интерактивного render, сообщение печатается один раз.

### Context Freshness

Не добавлять постоянный индикатор «контекст старый». Предупреждать только когда известное устаревание реально влияет на действие (например, файл был изменён с момента анализа и это подтверждено данными).

### Quiet Undo

Если операция имеет надёжный undo, он доступен в ограниченный и понятный промежуток времени. Нельзя показывать `Undo`, если операция необратима или undo не реализован. Для файловых изменений не подменять настоящий Git/diff механизм фиктивной отменой.

### No-Op Honesty

Если агент проверил задачу и не нашёл нужных изменений, финал говорит `No changes needed` или эквивалентно. Не создавать пустой diff и не выдавать отсутствие изменений за успех изменения кода.

### Stable Streaming

Текст ответа и tool events могут обновляться, но интерфейс не прыгает. Не делать перерисовку с миганием/полным clear-screen на каждый token. При прокрутке вверх действует Scroll Hold.

### Hover Intent — только как дополнение

Терминал не имеет универсального CSS hover. Для мыши можно использовать небольшую задержку перед показом вторичных подсказок, если mouse events включены. Но основное действие всегда доступно через клавиатуру.

## 8.2 Время и затухание

- fade — только визуальная иерархия, никогда не удаление информации;
- не менять яркость активного состояния произвольно;
- временные маркеры должны быть основаны на реальном времени событий;
- не делать частую перерасчётную анимацию при каждом token;
- motion modes: `none`, `quiet`, `normal`; default — `quiet`;
- reduced motion/off mode полностью выключает анимацию, при этом вся полезная информация сохраняется;
- не делать idle breathing логотипа в CLI;
- не воспроизводить звук.

## 8.3 Новые предложения специально для CLI

### A. Quiet Command History

Командная палитра и поиск сессий поддерживают быстрый фильтр и ограниченный список недавних команд/сессий, но не показывают их все на главном экране. Не записывать секреты из командной строки в историю.

### B. Diff Jump Map

В длинном diff показывать компактное `file 3/8 · hunk 2/5`. Клавиши переходят к следующему файлу или hunk без необходимости искать его в огромном выводе. Никакого миниатюрного цветного графика, только полезные координаты.

### C. Output Freeze

Клавиша временно фиксирует текущую картину вывода, пока агент продолжает работать. Счётчик сообщает `live output paused · 14 new events`; пользователь не теряет события и может вернуться к live view. Это отдельное от pause агента действие: оно замораживает просмотр, а не выполнение.

### D. Safe Command Preview

Перед risky command Nexora показывает нормализованную команду и рабочую директорию отдельными строками. Если команда может менять файлы, удалять данные или влиять за пределами workspace, это должно быть описано простым языком до approval. Не прятать shell-команду внутри непонятного описания инструмента.

### E. Workspace Boundary Hint

Если путь выходит за настроенную рабочую директорию, показать краткое предупреждение и классификацию. Сам факт пути не должен автоматически давать доступ: окончательное решение определяется общей permission policy.

### F. Event Density Guard

Если инструмент быстро производит сотни одинаковых событий, TUI может группировать их на экране, но должен сохранить оригинальный порядок, счётчики и путь к полному выводу. Не терять ошибки и не менять фактическую семантику событий.

### G. Terminal Restore Guarantee

После выхода, panic, ошибки и отмены CLI обязан вернуть исходные режимы терминала: cursor visibility, alternate screen, raw mode, mouse capture. Это не только polish: экран пользователя не должен оставаться сломанным после падения приложения.

### H. Honest Capability Mode

Если терминал не поддерживает нужные цвета, мышь или alternate screen, CLI продолжает работать в доступном режиме и показывает короткое объяснение только при необходимости. Не требовать пользователя сменить терминал ради базовых функций.

# 9. Команды и контракты обычного CLI

Команды — целевой интерфейс. Их нужно согласовать с уже существующими именами и поведением в репозитории перед реализацией, но семантика должна остаться понятной и стабильной.

## 9.1 Основные команды

```text
nexora
nexora --help
nexora --version
nexora run <prompt>
nexora resume [session-id]
nexora sessions list
nexora sessions open <session-id>
nexora sessions rename <session-id> <title>
nexora sessions archive <session-id>
nexora sessions delete <session-id>
nexora models list
nexora providers list
nexora config get <key>
nexora config set <key> <value>
nexora diff [session-id]
nexora doctor
nexora logs [--follow]
```

Это не обязательный перечень всех команд для первой поставки. Главное — согласованная грамматика, отсутствие неоднозначных синонимов и общий источник описаний/доступности команд.

## 9.2 `nexora run`

Целевые параметры, если соответствующая возможность уже поддерживается общим core:

```text
nexora run <prompt>
  --provider <id>
  --model <id>
  --mode <supervised|semi_autonomous|full_autonomous>
  --max-steps <n>
  --budget-usd <amount>
  --workspace <path>
  --format <text|json|jsonl>
  --plain
  --no-color
  --quiet
  --verbose
```

Правила:

- command-line override не меняет глобальные настройки молча;
- значения валидируются до запуска;
- default values совпадают с согласованными defaults core/Desktop там, где настройки общие;
- бюджет всегда отображается как ограничение/оценка, а не как гарантия фиксированной стоимости;
- `--mode full_autonomous` не отменяет глобальные опасные операции и permission boundary;
- если задан `--format json/jsonl`, stdout должен быть машинно-читаемым, без ANSI и рекламных banner;
- диагностические сообщения идут в stderr;
- `--quiet` уменьшает несущественный вывод, но не подавляет ошибки/approval safety messages;
- `--verbose` раскрывает диагностическую информацию без secrets.

## 9.3 Машиночитаемый вывод

Для `json` определить стабильный итоговый object. Для `jsonl`/NDJSON — одно JSON-событие на строку, например:

```json
{"type":"run_started","run_id":"...","session_id":"..."}
{"type":"tool_started","tool":"read_file","path":"src/auth.ts"}
{"type":"tool_completed","tool":"read_file","path":"src/auth.ts","ok":true}
{"type":"run_completed","status":"completed","duration_ms":18000}
```

Это иллюстрация формата, не реальная модель поля ID. Финальную схему нужно документировать, версионировать и не менять несовместимо без причины. Machine output не содержит formatted prose, terminal colors, progress spinners или секретов.

## 9.4 Exit codes

Использовать документированные коды, а не `1` для любого исхода. Целевая семантика:

- `0` — успешное завершение;
- отдельный non-zero code для пользовательской/валидационной ошибки;
- отдельный code для provider/network/auth failure;
- отдельный code для approval denied/cancelled, если это важно вызывающему скрипту;
- отдельный code для budget/spend limit exhaustion;
- отдельный code для internal/unexpected error.

Точные числовые значения должны быть определены одним enum/таблицей и сохранены между версиями, если возможно. В TUI exit code отражает итог последнего процесса/команды, а не просто факт, что пользователь закрыл интерфейс.

## 9.5 Пайпы и stdin

Если stdin содержит задачу или подключён pipe:

- не открывать полноэкранный TUI автоматически;
- не вставлять ANSI в redirected output;
- не ждать интерактивного ввода, если режим заявлен как non-interactive;
- если для продолжения нужен approval, завершать предсказуемо и объяснять, как повторить интерактивно или настроить разрешения;
- prompt может передаваться positional argument либо через поддерживаемый stdin mode;
- текстовый режим удобен человеку, JSONL — инструментам.

# 10. Поведение клавиатуры

Клавиатура — основной способ управления. Bindings не должны различаться хаотично между экранами.

| Клавиша | Общее значение |
|---|---|
| `↑ / ↓` | Перемещение по списку/истории, когда фокус не в многострочном editor |
| `← / →` | Перемещение по горизонтальным элементам/переключение detail tabs по контексту |
| `Enter` | Выбрать/отправить/подтвердить в зависимости от активного элемента |
| `Esc` | Закрыть верхний overlay или отложить действие; ничего опасного не подтверждает |
| `Ctrl+K` | Command palette |
| `Ctrl+J` | Новая строка в composer |
| `Ctrl+C` | Отменить active run или прервать текущий ввод; повторное поведение описано явно |
| `Ctrl+D` | Ввести EOF/выйти только когда это безопасно и не конфликтует с текущим состоянием |
| `Ctrl+Z` | Не использовать бездумно как универсальный undo; Windows host может перехватывать сочетание |
| `F1` | Help/keybindings |
| `F5` | Refresh state, если это действие действительно поддерживается |
| `Tab` | Перевод фокуса между областями; autocomplete — только когда открыт |
| `Shift+Tab` | Обратный перевод фокуса, если текущий terminal host передаёт событие |
| `PageUp/PageDown` | Прокрутка timeline/details |
| `Home/End` | Начало/конец истории или строки по контексту |

Каждая панель показывает только короткий список актуальных shortcuts. Полный список — help. Не показывать комбинации, которые текущий экран не поддерживает.

### Ctrl+C и выход

Ctrl+C не должен случайно убивать UI и оставлять tool process. Рекомендованная модель:

- когда run активен — первый `Ctrl+C` просит отменить run и показывает статус;
- пока отмена обрабатывается, повторный ввод не должен запустить второй запрос;
- если run уже idle и поле ввода пустое — `Ctrl+C` может попросить выход или очистить ввод согласно понятному состоянию;
- `Ctrl+Q` может быть явной командой выхода, если не конфликтует с host; она должна быть показана в help;
- при попытке выйти с активным run спросить/предложить cancel, если выход может оставить процесс или потерять контекст.

# 11. Безопасность и управление агентом

## 11.1 Не снижать безопасность ради удобства TUI

CLI не является «автоматическим» только потому, что он работает в терминале. Общая permission policy должна действовать одинаково в Desktop и CLI.

Обязательные принципы:

- команды и filesystem tools ограничиваются workspace/policy;
- операции вне workspace не считаются безопасными только из-за предоставленного пути;
- destructive commands требуют соответствующего подтверждения;
- stdout/stderr внешней программы — untrusted content;
- prompt/tool output не может менять разрешения или менять собственные правила безопасности;
- parked approvals не разрешаются автоматически после timeout/закрытия панели;
- denied action отображается как denied и не маскируется под provider failure;
- API keys, tokens, authorization headers и чувствительные environment variables не попадают в экран/лог по умолчанию;
- если процесс отменён, UI подтверждает отмену только после фактического состояния core/process.

## 11.2 Режимы автономности

Использовать общий набор режимов, который поддерживает Nexora core:

- `supervised`;
- `semi_autonomous` (текущий default, если он остаётся default core);
- `full_autonomous`.

CLI не должен самостоятельно изобретать четвёртый режим или переопределять значения режимов. В status line достаточно короткого label; в approval/details видны последствия текущего режима.

## 11.3 Pause, resume, cancel, extend budget

Эти операции выполняются через общие use cases. TUI отражает действительный lifecycle:

- `pause requested` не равен `paused`;
- `resume requested` не равен `running`;
- cancel остаётся pending до фактического завершения;
- extend budget показывает новый установленный лимит только после подтверждения core;
- лимит шагов и денежный лимит — разные понятия и должны иметь разные подписи;
- если provider/tool не поддерживает безопасную немедленную отмену, пользователь получает понятный статус.

# 12. Доступность, fallback и качество терминала

## 12.1 Уважать среду пользователя

CLI должен нормально работать в:

- Windows Terminal;
- PowerShell 7;
- Windows PowerShell 5.1;
- встроенном терминале VS Code;
- Windows Console/ConPTY в пределах поддерживаемых возможностей;
- redirected output / CI в обычном текстовом режиме.

Не считать все эти среды одинаковыми. Ввод мыши, передача некоторых сочетаний клавиш, UTF-8 и цветовые возможности различаются по host/settings.

## 12.2 Capability detection

При запуске определить доступные возможности настолько надёжно, насколько позволяет окружение:

- stdin/stdout интерактивны или перенаправлены;
- доступен ли полноэкранный alternate screen/raw mode;
- уровень цвета;
- Unicode/ASCII display mode;
- размер окна;
- поддерживаются ли mouse events, если они включены;
- не запущен ли CLI в среде, где ANSI требуется отключить.

Предоставить override flags, если auto detection ошибается. При ошибке alternate screen не прекращать все возможности — переключаться в inline/simple mode там, где это безопасно.

## 12.3 Восстановление терминала

Захват терминала должен иметь RAII/guard-подобную защиту. На normal exit, error и panic приложение обязано попытаться восстановить raw mode, alternate screen, cursor visibility и mouse capture.

Не оставлять пользователя с невидимым курсором, поломанным echo ввода или захваченными shortcuts после аварии.

## 12.4 Reduced motion

У CLI нет web `prefers-reduced-motion`, поэтому использовать собственную настройку, например `motion = "quiet" | "none" | "normal"`.

Default: `quiet`. В режиме `none` отключается всё декоративное движение, но статусы, порядок событий, счетчики и сообщения остаются. Spinner не должен быть единственным доказательством работы — рядом должен быть текстовый статус.

## 12.5 Доступность без цвета

Терминал должен оставаться понятным при:

- no-color mode;
- низкой контрастности;
- отключённой анимации;
- ASCII mode;
- увеличенной ширине символов/необычном шрифте.

Ошибка отличается от успеха не только цветом: `! Failed` против `✓ Done`, с текстовой подписью. Активный пункт списка имеет cursor/marker и контраст, а не только другой цвет.

# 13. Производительность

CLI должен ощущаться мгновенным для локальных действий.

Цели поведения:

- root command/help/version не ждут инициализации AI provider;
- открытие TUI не требует сети;
- history browsing/search не вызывает модель;
- изменение темы/цвета и открытие palette — локальные операции;
- каждое новое token/event не приводит к полному мерцающему экрану;
- дорогой diff parsing не должен блокировать keyboard input;
- большие outputs виртуализируются/ограничиваются для отображения, сохраняя возможность доступа к полному результату;
- запросы к модели не мешают прокрутке, открытию справки и просмотру уже полученных результатов;
- отключённые/не настроенные providers не пробуются в фоне без явного запроса пользователя.

Не вводить отдельные фоновые сервисы, telemetry или синхронизацию без отдельного решения. CLI запускается быстро и не держит daemon-процесс без необходимости.

# 14. Конфигурация

Настройки должны использовать общий источник правды там, где они являются общими с Desktop.

Примеры настраиваемых значений:

- default provider/model;
- autonomy mode;
- workspace root/default working directory;
- max steps / spend guard, если эти настройки поддерживаются core;
- terminal color mode;
- ASCII/Unicode rendering;
- mouse enabled/disabled;
- motion `quiet/none/normal`;
- composer/keybindings, если добавляется remapping;
- default output format для non-interactive commands;
- log verbosity.

Требования:

- `nexora config get/set` использует allow-listed известные ключи;
- секреты нельзя читать/записывать через обычный config key, если они должны храниться в keyring;
- значения валидируются и ошибки объясняют допустимый формат;
- неизвестный config key не записывается молча;
- временный CLI override не заменяет persistent setting;
- изменения применяются предсказуемо и не ломают уже идущий run;
- help показывает допустимые значения.

# 15. Логи, диагностика и приватность

## 15.1 Логи

Логи нужны для debugging, но не должны превращаться в пользовательский интерфейс. Основные события отображаются через структурированные run events. Диагностические логи доступны отдельно.

Не логировать:

- API keys;
- authorization headers;
- сырые тела provider requests/responses, если там есть private prompt/files/secrets;
- opaque provider-specific reasoning signatures;
- полный sensitive environment;
- содержимое секретных файлов.

Ошибки core классифицируются и переводятся в краткое human-readable сообщение. Сырой error detail можно раскрыть/сохранить локально, если он предварительно sanitised.

## 15.2 Local-first

- запуск CLI не должен автоматически отправлять данные в сеть;
- данные уходят к AI provider только в рамках явного действия пользователя/запущенного run;
- нет обязательной телеметрии, аккаунта или cloud sync;
- команды `doctor` и `--version` работают offline;
- экспорт истории должен быть явным;
- история и local search используют общую local database там, где применимо.

# 16. Производственная устойчивость и обработка ошибок

Каждая ошибка должна отвечать на три вопроса:

1. Что произошло?
2. Что сохранилось / что не произошло?
3. Какое следующее действие доступно?

Примеры:

```text
Provider unavailable
Could not reach OpenRouter. Your draft is preserved.
Check connection or choose another provider.
```

```text
Credential rejected
The provider rejected the configured key. The key was not shown or logged.
Open provider settings to replace it.
```

```text
Workspace access denied
The requested path is outside the allowed workspace.
No file operation was performed.
```

Ошибки должны иметь устойчивые типы в core. UI не должен определять их по текстовому совпадению. Идентичное исходное событие должно классифицироваться одинаково в Desktop и CLI.

Не обещать, что операция не произошла, если ошибка случилась после частичного выполнения. При частичном эффекте показывать известное состояние и доступные способы проверки.

# 17. Тестируемость и критерии качества

## 17.1 Автоматические тесты

- unit tests для command parsing/validation;
- tests для exit code mapping;
- tests для config validation и redaction;
- tests общего agent core остаются authoritative;
- TUI snapshots/render tests через Ratatui TestBackend;
- тесты resize: большой, обычный и узкий терминал;
- no-color/ASCII test mode;
- тесты потока событий, scroll hold и сохранения draft/viewport;
- tests approvals: pending не авторазрешается; cancel/deny/approve имеют разный результат;
- tests отмены процесса и восстановления управления;
- тесты, что ANSI не попадает в redirected/plain/JSON output;
- tests на secret redaction;
- tests совместного доступа Desktop/CLI к SQLite и миграциям;
- smoke tests в реальных Windows Terminal и VS Code Terminal перед выпуском.

## 17.2 Acceptance criteria

CLI считается соответствующим этому brief, если:

1. `nexora --help` и `nexora --version` быстро работают без сети и без TUI.
2. `nexora` в интерактивном терминале открывает рабочий TUI, а не веб/desktop окно.
3. `nexora` при redirected output не запускает полноэкранный UI неожиданно.
4. Запрос модели/работа tool не блокирует input, scroll и просмотр деталей.
5. Пользователь может подняться по history во время streaming и не быть насильно возвращён вниз.
6. Черновик остаётся на месте при открытии overlay и при ошибке отправки.
7. Approval имеет понятное описание операции и не auto-approves после закрытия экрана.
8. Diff можно открыть и закрыть без потери позиции в run.
9. Старые tool calls сворачиваются только как представление; их подробности доступны и порядок не теряется.
10. Никакие сведения о ключах или auth headers не оказываются в UI/log/JSON output.
11. В no-color + ASCII mode весь essential workflow остаётся доступным.
12. При выходе/ошибке терминал возвращается в корректное состояние.
13. CLI и Desktop используют общую business logic, provider registry, credential namespace и schema/migrations там, где эти контракты общие.
14. Внешний вид остаётся спокойным во время длительного run: никаких постоянных flash/pulse/цветового шума.
15. В обычном non-interactive режиме stdout имеет стабильный формат и exit code отражает фактический результат.

# 18. Чего нельзя делать при реализации

- Не портировать CSS/React компоненты буквально в терминал.
- Не создавать новую реализацию agent runner только для CLI.
- Не дублировать provider/model registry.
- Не создавать отдельный SQLite schema без причины.
- Не писать credentials в файл или command arguments.
- Не менять поведение safety/approval policy в CLI относительно Desktop.
- Не выдумывать agent states или progress, которых не выдаёт core.
- Не делать весь вывод цветным ради «современности».
- Не использовать emoji/Nerd Font как обязательную зависимость.
- Не делать mouse-only UX.
- Не скрывать errors и pending approvals при auto-fold.
- Не удалять run events из истории при fade/folding.
- Не менять UI layout на каждом этапе выполнения.
- Не запускать тесты/команды в workspace без соответствующего действия пользователя и permission policy.
- Не отправлять запрос к модели в `doctor`, help или при открытии приложения.
- Не добавлять Telegram/cloud accounts/sync/telemetry в scope CLI автоматически.
- Не путать «TUI output paused» с «agent paused» — это разные состояния.
- Не печатать decorative banner при использовании JSON/pipe output.

# 19. Финальное визуальное направление

**Название:** Quiet Terminal Workspace  
**Фирменный элемент:** Agent Activity Spine  
**Главная идея:** состояние агента наблюдаемо, но сам интерфейс не требует постоянного внимания.

Визуальные правила в одной строке:

```text
terminal-native
quiet by default
compact but readable
one muted accent
semantic status labels
stable layout
keyboard-first
no-glow
no-glass
no-emoji dependency
no fabricated progress
no forced autoscroll
no surprise modal takeover
```

В CLI Nexora должен быть приятным не потому, что экран постоянно двигается, а потому, что после нескольких часов использования пользователь знает, где он, что делает агент, где находятся изменения и как остановить/проверить/продолжить работу — не борясь с интерфейсом.

**Рекомендация по приоритету UX, не по срокам разработки:** сначала обеспечить общие core-контракты, честные события, scroll hold, approvals, draft/focus memory, diff и plain mode. После этого добавлять временные визуальные следы и остальные micro-interactions.

## Итоговое решение

Создавать Nexora CLI как самостоятельный Rust-бинарник с двумя режимами — **интерактивный TUI** и **обычный script-friendly CLI**. Для TUI использовать Ratatui + Crossterm, для команд — Clap. Общую agent/provider/storage/permission logic отделить от Tauri shell и использовать из обоих приложений. Дизайн строить вокруг спокойного event timeline, сохранения контекста, безопасного контроля агента и стабильного терминального поведения.

Это целевой product/design/architecture brief. Он намеренно **не содержит пошагового плана реализации**: порядок работ и декомпозицию задач можно определить отдельно после аудита текущих зависимостей репозитория.
